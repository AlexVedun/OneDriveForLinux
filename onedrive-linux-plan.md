# План разработки клиента OneDrive для Linux

Дата: 2 октября 2026 года  
Статус: проектный план, реализация ещё не начата

## 1. Цель и границы проекта

Создать настольное приложение для **личного OneDrive** с двумя режимами работы:

1. **Синхронизируемая папка:** двусторонняя синхронизация выбранных папок, локальная копия доступна без сети.
2. **Виртуальный диск:** дерево OneDrive доступно через FUSE; содержимое файлов загружается по запросу и при необходимости остаётся в кэше.

Приложение имеет окно настройки и просмотра состояния, работает в фоне после закрытия окна, отображает меняющийся значок в системном трее и распространяется как AppImage. Первый публичный выпуск ориентирован на один личный аккаунт Microsoft на одного пользователя Linux. Архитектура должна позволять добавить несколько аккаунтов позже.

Под «аналогом официального клиента» в первом выпуске понимаются операции с файлами, надёжная синхронизация и понятное состояние программы. Совместное редактирование документов Office, интеграция с проводником Windows, резервирование системных папок по правилам Windows и корпоративные политики в первый выпуск не входят. Это отдельные продуктовые функции, а не обязательные части движка синхронизации.

## 2. Принятые технические решения

| Часть | Решение | Причина |
|---|---|---|
| API | Microsoft Graph `v1.0` | Официальный рекомендуемый API для OneDrive, включая личные аккаунты. |
| Авторизация | OAuth 2.0 Authorization Code + PKCE через системный браузер; Device Code как резервный способ | Без встроенного клиентского секрета; подходит настольному приложению. |
| Язык | Rust | Один стек для фонового процесса, GUI и FUSE; строгая модель владения полезна для параллельной обработки файлов. |
| Окно | GTK 4 + libadwaita | Нативный интерфейс Linux и поддерживаемые Rust-привязки. |
| Обмен GUI с движком | Пользовательская шина D-Bus | GUI может закрываться независимо от фонового процесса. |
| Метаданные и очередь | SQLite с WAL и миграциями схемы | Восстановление после перезапуска и транзакционное сохранение прогресса. |
| Виртуальный диск | FUSE 3, отдельный модуль поверх общего каталога и кэша | Доступ по запросу через обычные файловые менеджеры. |
| Трей | StatusNotifierItem и DBusMenu | Изменение значка и меню в окружениях с поддержкой системного трея. |
| Распространение | AppImage x86_64; другие архитектуры после отдельной проверки | Один переносимый файл для первого выпуска. |

Окончательные версии библиотек закрепить перед началом сборки и обновлять после проверки совместимости. Не привязывать бизнес-логику к конкретному GUI или реализации FUSE.

## 3. Архитектура процессов и данных

```text
┌───────────────────────────┐       D-Bus       ┌──────────────────────────────┐
│ GUI + трей                │◄─────────────────►│ Фоновый процесс              │
│ вход, настройки, события  │                    │ очередь, синхронизация, FUSE │
└───────────────────────────┘                    └──────────────┬───────────────┘
                                                              │
                                          ┌───────────────────┼───────────────────┐
                                          ▼                   ▼                   ▼
                                     Microsoft Graph       SQLite          Кэш файлов
```

Фоновый процесс единолично изменяет базу состояния и выполняет операции Graph. GUI получает снимок состояния и события через D-Bus, отправляет команды: пауза, возобновление, изменение настроек, вход, выход, монтирование. При отсутствии GUI синхронизация и FUSE продолжают работать.

Основные модули:

- **auth:** регистрация приложения, получение и обновление токенов, безопасное хранение учётных данных.
- **graph:** запросы к `/me/drive`, чтение каталога, `delta`, скачивание, изменение метаданных, удаление и возобновляемая загрузка.
- **catalog:** локальная модель дерева по `drive_id + item_id`, версии, признаки удаления и связи с путями.
- **sync:** сравнение локального, удалённого и последнего подтверждённого состояний; планирование операций; разрешение конфликтов.
- **transfer:** загрузка/скачивание, лимиты параллелизма и скорости, повторы, прогресс.
- **cache:** локальные копии для виртуального диска, закрепление файлов офлайн и очистка по лимиту.
- **mount:** FUSE-операции над виртуальным деревом.
- **desktop:** GUI, трей, уведомления, автозапуск и интеграция AppImage.

**Одна и та же локальная папка не может одновременно быть папкой синхронизации, точкой монтирования или кэшем.** При изменении путей это проверяется до сохранения настроек, включая вложенные пути и символические ссылки.

## 4. Регистрация приложения и вход

1. Зарегистрировать приложение с поддержкой личных аккаунтов Microsoft и как public client. Зафиксировать `client_id` в сборке; клиентский секрет не создавать.
2. Запрашивать минимальный набор делегированных прав для полного клиента: `Files.ReadWrite` и `offline_access`. Запрашивать дополнительные права только для добавленной функции, которой они нужны.
3. Основной сценарий — системный браузер, Authorization Code + PKCE и обратный вызов на loopback-адрес. Резервный сценарий — Device Code для окружений, где браузерный возврат не работает.
4. Использовать библиотеку авторизации либо собственный тонкий слой с проверкой `state`, PKCE и обработкой обновления токена. Секреты хранить через системное хранилище секретов; если его нет — предоставить защищённое локальное хранилище с разблокировкой пользователем. Не писать токены в журнал.
5. Показывать в GUI состояние «требуется вход», имя аккаунта и возможность выйти. После выхода останавливать сетевые операции и размонтировать виртуальный диск перед удалением токенов. Локальные файлы удалять только по отдельному явному действию пользователя.

## 5. Модель состояния

Минимальные сущности SQLite:

| Сущность | Поля и назначение |
|---|---|
| `account` | ID аккаунта, ID диска, метаданные пользователя, состояние авторизации. |
| `remote_item` | `drive_id`, `item_id`, `parent_id`, имя, тип, размер, `eTag`/`cTag`, время, флаг удаления. |
| `local_item` | Относительный путь, идентификатор файловой системы при наличии, размер, время, локальный хеш при необходимости, флаг грязной копии. |
| `mapping` | Связь удалённого ID с локальным путём и последним подтверждённым состоянием. |
| `delta_cursor` | Полный URL `@odata.deltaLink`, сохраняемый после завершения и применения страницы изменений. |
| `operation` | Тип, объект, ожидаемая версия, статус, число попыток, причина ошибки, идемпотентный ключ. |
| `transfer` | Файл, направление, смещение, временный путь, сведения о сессии загрузки и срок её действия. |
| `cache_entry` | Удалённый ID и версия, путь в кэше, размер, последнее обращение, закрепление офлайн. |
| `settings` | Режимы, пути, выбранные папки, интервалы, лимиты, автозапуск. |

Инварианты:

- Ключ удалённого объекта — ID, а не путь. Переименование или перемещение не меняет его личность.
- Незавершённая загрузка не считается опубликованной. Незавершённое скачивание не заменяет пригодный локальный файл.
- Применение `delta` и продвижение курсора фиксируются транзакционно: после сбоя изменения можно безопасно прочитать снова.
- Удаление и перезапись требуют сравнения с последним подтверждённым состоянием; сомнение трактуется как конфликт с сохранением обеих копий.

## 6. Алгоритм синхронизации папки

### Первое подключение

1. Получить информацию о диске, проверить доступное место и права.
2. Прочитать полное дерево через `/me/drive/root/delta`, пройти все `@odata.nextLink`, сохранить метаданные и итоговый `@odata.deltaLink`.
3. Сканировать локальную папку. Сопоставить уже существующие файлы по безопасным признакам; при неоднозначности не перезаписывать автоматически.
4. Показать предварительный итог: сколько файлов будет загружено, скачано, пропущено или потребует решения.
5. Применить план, сначала создавая каталоги, затем передавая файлы, затем обрабатывая удаления. Завершение каждой операции сохранять отдельно.

### Постоянная работа

- Локальные события получать через файловый монитор; после переполнения очереди или перезапуска проводить контрольное сканирование.
- Удалённые изменения получать через `delta` с периодическим опросом и опросом при возвращении сети. Интервал сделать настраиваемым в разумных пределах; не строить обычный Linux-клиент на webhook, которому нужен общедоступный HTTPS-адрес.
- Состояние рассчитывать по трём версиям: последнее подтверждённое общее состояние, текущий локальный файл и текущий удалённый объект.
- Операции ставить в устойчивую очередь; переносить и переименовывать по ID, где это возможно. Проверять ожидаемую версию через `If-Match` или эквивалентные условия API.
- Крупные файлы загружать через upload session, сохранять прогресс и возобновлять передачу. Размер фрагмента выбирать кратным 320 КиБ. Скачивать во временный файл и атомарно заменять целевой после проверки размера и содержимого.
- При `429`/`503` соблюдать `Retry-After`; при временных ошибках использовать ограниченные повторы. После потери `delta`-курсора (`410 Gone`) провести повторное перечисление и согласование без безусловного удаления локальных данных.

### Правила конфликтов и крайние случаи

- **Оба изменили содержимое:** сохранить удалённую и локальную версии, назвать конфликтную копию однозначно и показать событие пользователю.
- **Локальное изменение против удалённого удаления:** не удалять локальную версию; предложить восстановление или сохранение конфликтной копии.
- **Удалённое изменение против локального удаления:** не удалять удалённую версию до повторной проверки.
- **Переименование каталога:** перестроить дочерние локальные пути по ID, поскольку `delta` не обязан возвращать всех потомков.
- **Символические ссылки:** в первом выпуске не переходить по ним при обходе синхронизируемой папки; явно показывать пропуск.
- **Несовместимые имена:** заранее проверять запрещённые OneDrive символы и имена, различающиеся только регистром. Показывать список пропусков; не делать скрытое переименование.
- **Массовые удаления:** временно приостанавливать выполнение и запрашивать подтверждение в GUI после настраиваемого порога.
- **Квота и нехватка локального места:** приостанавливать соответствующее направление и показывать точную причину.

## 7. Виртуальный диск через FUSE

Режим виртуального диска использует тот же каталог метаданных, но собственную точку монтирования и отдельный кэш. В первой версии виртуального режима обеспечить чтение и базовые операции, затем добавить запись.

1. **Чтение:** `lookup`, `getattr`, `readdir`, `open`, `read`. Каталоги строятся из локальной базы; отсутствующее содержимое скачивается при открытии. Для больших файлов изучить и реализовать диапазонное чтение там, где оно надёжно поддерживается; до этого скачивать целый файл с явным показом ожидания.
2. **Кэш:** хранить по ID и версии, не по видимому имени; проверять версию перед повторным использованием. Лимит места и «доступно офлайн» настраиваются в GUI. Не удалять закреплённые или грязные файлы.
3. **Запись:** использовать локальный временный файл. Успех записи означает надёжное сохранение локально, а не завершение загрузки в облако. GUI и трей должны отличать эти состояния. После закрытия/синхронизации ставить отправку в очередь. Ошибку передачи показывать до решения пользователя.
4. **Размонтирование:** при завершении сессии остановить новые операции, дождаться локальной фиксации открытых записей и корректно размонтировать. После аварийного завершения обнаруживать оставшуюся точку монтирования.
5. **Недоступность FUSE:** режим синхронизируемой папки и окно продолжают работать. Диагностика показывает, чего не хватает: библиотека, `/dev/fuse`, разрешение на монтирование или занятая точка.

На старте виртуальный диск не должен автоматически загружать всё содержимое OneDrive. Точка монтирования не может находиться внутри синхронизируемой папки или кэша.

## 8. Оконный интерфейс

### Первый запуск

Пошаговая настройка: вход → выбор режима → путь локальной папки → выбор папок → путь виртуального диска и лимит кэша → предварительный итог первой синхронизации → запуск.

### Основное окно

- **Обзор:** учётная запись, связь, состояние обоих режимов, последние ошибки и время последней успешной проверки.
- **Активность:** очередь передач, прогресс по файлам и общий прогресс, история ошибок, повтор операции.
- **Папки:** дерево OneDrive и выбор синхронизируемых разделов.
- **Виртуальный диск:** монтирование/размонтирование, точка, объём кэша, закреплённые файлы.
- **Настройки:** автозапуск, опрос, ограничения скорости, уведомления, действия при конфликте, диагностика.
- **Диагностика:** версия приложения, статус FUSE и трея, проверка доступа к Graph, экспорт журнала без токенов и временных ссылок скачивания.

Все длительные действия асинхронны. Интерфейс остаётся отзывчивым при сканировании дерева, передаче большого файла и потере сети. Закрытие окна скрывает его; синхронизация продолжается. Пункт «Выход» завершает приложение после безопасного сохранения состояния.

## 9. Трей и модель состояний

Реализовать StatusNotifierItem с меняющимся именем/пиктограммой и текстовой подсказкой:

| Приоритет | Состояние | Значок и подпись |
|---:|---|---|
| 1 | Требуется вход / ошибка, требующая действия | Предупреждение с краткой причиной. |
| 2 | Нет сети | Облако без соединения. |
| 3 | Приостановлено пользователем | Пауза. |
| 4 | Идёт передача | Круговые стрелки; в меню число операций. |
| 5 | Проверка изменений | Индикатор проверки. |
| 6 | Всё синхронизировано | Галочка и время проверки. |

Меню: открыть окно, открыть папку, открыть виртуальный диск, пауза/возобновление, запустить проверку, выйти. Не менять пиктограмму на каждом переданном блоке; обновлять при переходе состояния. Значение состояния всегда доступно текстом и в основном окне.

При отсутствии хоста StatusNotifierItem (например, в GNOME без соответствующего расширения) приложение остаётся доступным через ярлык и окно; критические события также показываются уведомлениями. В установочном экране объяснить зависимость отображения трея от окружения рабочего стола.

## 10. AppImage, интеграция и обновления

1. Собрать релиз на достаточно старой поддерживаемой базе Linux; зафиксировать минимальные версии системных библиотек и протестировать запуск на целевых дистрибутивах.
2. Сформировать AppDir: `AppRun`, бинарные файлы, GTK-библиотеки/ресурсы, `.desktop`, статическая и статусные иконки, лицензии. Проверить, какие системные библиотеки нельзя или не следует упаковывать.
3. Собирать AppImage в CI, публиковать SHA-256 и подпись выпуска. Проверять запуск скачанного файла, а не только программы из дерева сборки.
4. Предусмотреть «Интегрировать в систему»: копия AppImage в постоянный пользовательский каталог, ярлык приложения и автозапуск фонового режима. Не писать автозапуск на произвольный путь к файлу, который пользователь может переместить.
5. Обновление: скачать новый AppImage, проверить подпись и контрольную сумму, завершить или безопасно перезапустить процесс, переключить постоянный ярлык на новую версию. Не менять исполняемый файл, из которого сейчас смонтирован работающий AppImage.
6. Проверить отдельно FUSE, который нужен самому AppImage, и FUSE 3 для виртуального диска. Если AppImage не может смонтировать свой образ, предоставить документированный запуск через `--appimage-extract-and-run`; если виртуальный FUSE недоступен, оставить режим синхронизации.

Данные приложения размещать по XDG: конфигурация — `XDG_CONFIG_HOME`, база и постоянное состояние — `XDG_STATE_HOME`/`XDG_DATA_HOME`, временный кэш — `XDG_CACHE_HOME`. Конкретные пути показать в диагностике. Обновление или удаление AppImage не должно удалять пользовательские файлы и локальный кэш автоматически.

## 11. Этапы разработки и критерии готовности

### Этап 0. Каркас и проверка доступа

- Создать репозиторий, сборку Rust, форматирование, линтер, журналирование и CI.
- Зарегистрировать тестовое приложение Microsoft и проверить вход личного аккаунта.
- Создать минимальное окно, фоновый процесс и D-Bus-команду `status`.

**Готово, когда:** AppImage открывает окно на целевой Linux-системе; вход выполняется без передачи пароля приложению; после закрытия окна фоновый процесс продолжает отвечать.

### Этап 1. Каталог OneDrive и режим только чтения

- Получать полное дерево и `delta`, хранить курсор и элементы по ID.
- Показывать дерево, размер, время изменения и ошибки в GUI.
- Скачивать выбранный файл через временный файл с безопасной заменой.

**Готово, когда:** повторный запуск не перечитывает всё дерево без причины; переименование и удаление на веб-сайте видны в приложении; прерванное перечисление восстанавливается без потери состояния.

### Этап 2. Двусторонняя синхронизация

- Локальный монитор, очередь операций, загрузка, удаление и переименование.
- Возобновление крупных загрузок, контроль версий, конфликтные копии, пауза.
- Выбор папок и предварительный план первого запуска.

**Готово, когда:** создание, изменение, перемещение и удаление файлов проходят в обе стороны; отключение сети и аварийный перезапуск не теряют локальных правок; конфликт сохраняет обе версии; массовое удаление не выполняется молча.

### Этап 3. Полноценный desktop UX

- Настройки путей и скорости, очередь, история ошибок, уведомления.
- Трей с приоритетами состояния и действиями, автозапуск, интеграция AppImage.

**Готово, когда:** окно можно закрыть без остановки синхронизации; статус в трее соответствует статусу движка; пользователь может понять причину паузы или ошибки и исправить её из GUI.

### Этап 4. Виртуальный диск: чтение

- FUSE-каталоги и чтение с загрузкой по запросу.
- Кэш с лимитом, закрепление офлайн, монтаж/размонтаж из GUI.

**Готово, когда:** файловый менеджер показывает дерево без полной загрузки; открытый файл читается корректно; повторное чтение использует кэш; отключение сети даёт понятную ошибку для нескачанного файла и сохраняет доступ к закреплённым.

### Этап 5. Виртуальный диск: запись и выпуск

- Локальные грязные копии, очередь отправки, согласование с обычным режимом, восстановление после сбоя.
- Проверка AppImage на целевых системах, обновление, документация, пакет сценариев приёмки.

**Готово, когда:** запись через обычный редактор сохраняется локально и затем появляется в OneDrive; при сетевой ошибке данные не пропадают; оба режима могут работать одновременно без циклов и дублирования.

## 12. Проверка качества

Обязательные сценарии автоматической и ручной проверки:

- Авторизация, обновление токена, отзыв доступа, повторный вход.
- Пустой диск, глубокое дерево, много мелких файлов, крупный файл, Unicode и специальные символы.
- Локальные и удалённые изменения одного файла, переименования и перемещения каталогов.
- Отключение сети в середине скачивания и загрузки, перезапуск процесса в любой стадии.
- `429`, `503`, истёкший upload session, `410 Gone`, исчерпанная квота.
- Неожиданное удаление большого числа файлов, нехватка места, заполненный кэш.
- Одновременная работа двух режимов, открытые файлы при размонтировании.
- Запуск AppImage, трей и автозапуск на выбранных версиях GNOME, KDE Plasma и хотя бы одном более лёгком окружении.

Для интеграционных испытаний использовать отдельный тестовый личный OneDrive и временные папки. Разрушающие сценарии запускать только на тестовых данных. До публичного выпуска провести длительную пробную синхронизацию с контрольной сверкой содержимого и журналом необработанных расхождений.

## 13. Главные риски и решения

| Риск | Мера |
|---|---|
| Потеря данных из-за ошибочного удаления или конфликта | Трёхстороннее сравнение, условные запросы, конфликтные копии, порог массового удаления, транзакционная очередь. |
| Неполная или устаревшая `delta` | Хранить курсор только после применения изменений; при `410 Gone` повторно перечислять и согласовывать. |
| Ограничение частоты Graph | `Retry-After`, ограничение параллелизма, адаптивный опрос, отсутствие полного сканирования на каждом цикле. |
| Различия имён между Linux и OneDrive | Проверка до отправки, видимый список несовместимых файлов, явное разрешение конфликтов регистра. |
| Нет FUSE или трея в окружении | Независимость режима обычной синхронизации, понятная диагностика, доступ к окну через ярлык. |
| Перемещённый AppImage ломает автозапуск | Копия в постоянном каталоге при интеграции; обновление через переключение версии. |
| Утечка токенов или временных URL | Системное хранилище секретов, очистка логов, ограниченные права локальных файлов. |

## 14. Вопросы, которые нужно зафиксировать перед началом реализации

Эти решения не блокируют проектирование движка, но влияют на поведение продукта:

1. Минимальные поддерживаемые дистрибутивы и версии Linux; отдельно указать архитектуру CPU.
2. Нужна ли синхронизация общих папок, добавленных в личный OneDrive, в первом выпуске.
3. Нужно ли синхронизировать скрытые файлы и какие каталоги исключать по умолчанию.
4. Допустим ли пользовательский запрос подтверждения при массовом удалении даже при закрытом окне; предлагаемый безопасный вариант — остановка очереди до открытия GUI.
5. Предпочитаемый язык интерфейса в первом выпуске; заложить локализацию строк с начала разработки.
